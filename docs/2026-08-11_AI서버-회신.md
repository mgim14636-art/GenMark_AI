**엔드포인트가 없어 `FAILED`로 끝나던 상태는 해소되었습니다.**

`FastApiBrandKitAiClient`와 `BrandKitProcessor.buildRequest`를 직접 확인하고 거기에 맞췄습니다. **백엔드는 코드를 한 줄도 안 고치셔도 지금 바로 동작합니다.** 아래 3·4번은 품질을 올리기 위한 후속 작업이지 연동 조건이 아닙니다.

## 1. 3-3 협의 항목 4가지에 대한 답

### ① 엔드포인트를 하나로 할지 둘로 나눌지 → **하나 유지**

`POST /api/v1/generation/brand-kit`에서 `kit_type`으로 분기합니다. 배경 소스만 다르고 로고 합성 로직은 공유라 나눌 이유가 없습니다.

### ② 로고를 어떻게 넘길지 → **Base64 유지**

AI 서버는 백엔드 스토리지에 접근 권한이 없어 `storage_key`를 읽지 못합니다. `/similarity/search`도 이미 Base64로 받고 있어 일관됩니다. `data:image/png;base64,` 접두어가 붙어 있어도 처리합니다.

### ③ 응답 키 이름 → **최상위 `imageBase64` 유지 + `images[]` 추가**

`FastApiBrandKitAiClient`가 `body.get("imageBase64")`를 읽고 있어서, 그 자리를 그대로 채웁니다.

```json
{ "kitType": "BUSINESS_CARD",
  "imageBase64": "...",
  "images": [ { "imageBase64": "...", "width": 1063, "height": 591 } ],
  "preliminary": false, "warnings": [], "elapsedMs": 1447 }
```

`images[]`는 `/generate`의 `logos[].imageBase64`와 형태를 맞춘 정식 필드이고, 명함 앞/뒤나 썸네일 각도 변형이 추가될 여지를 둔 것입니다. 최상위 `imageBase64`는 그 첫 장을 복제한 호환 필드입니다.

**클라이언트 코드를 지금 고치실 필요는 없습니다.** 여유 있을 때 `images[]`로 옮기시면 됩니다.

### ④ 소요 시간 → **명함 1.5초 / 썸네일 최종 10~15초, 타임아웃 60초**

명함은 외부 API를 쓰지 않아 1.2~1.5초로 끝납니다. 썸네일은 FLUX 배경이 붙으면 10~15초를 예상합니다. `/generate`와 같은 기준으로 **타임아웃 60초**를 권장드립니다.

## 2. 산출 방식 — 로고를 이미지 생성 모델에 넣지 않습니다

현재 FLUX 호출부는 `prompt / width / height / seed / steps / samples`만 보내는 text-to-image 전용 경로입니다. 설령 image-to-image가 열려도 디퓨전 모델은 입력 로고를 그대로 재현하지 못합니다. **브랜드 아이덴티티 산출물에서 사용자 로고가 변형돼 나오면 기능 자체가 무의미해집니다.**

그래서 배경만 생성하고 로고는 정확히 합성하는 방식으로 갑니다. 기획서 (7) 수행방법에 이미 같은 방침이 적혀 있습니다 — *"CI 명함: 정보 정확도 확보를 위해 이미지 생성 모델 미사용"*.

## 3. 요청서에 빠져 있던 항목 — `card_info`

요청서 3-2 예시 본문에는 **명함에 인쇄할 사용자 정보가 없습니다.** 이 값이 없으면 명함에 넣을 내용이 없어, 신규 필드로 정의했습니다.

```json
"card_info": {
  "name": "남현욱", "title": "대표", "company": "주식회사 젠마크",
  "phone": "010-1234-5678", "email": "wook@genmark.ai",
  "address": "광주광역시 남구 송암로 60"
}
```

`BrandKitProcessor.buildRequest`가 현재 `kit_type / logo_image_base64 / survey / ci_bi` 네 가지만 보내고 있어서, 이걸 필수로 잡으면 **CI 브랜드킷이 전부 FAILED로 끝납니다.** 그래서 선택 항목으로 두었습니다.

- 없으면 회사명만 넣은 브랜드 카드로 합성되고, `preliminary: true` + `warnings`로 알립니다
- 레이아웃은 동일하므로 나중에 값이 채워지면 그대로 명함이 됩니다
- `name` 외에는 모두 선택이며, 빈 항목은 레이아웃에서 통째로 생략됩니다

**`Member`에 `name`과 `email`이 이미 있으니, 화면 없이도 그 둘만 먼저 채워 보내실 수 있습니다.** 직함·연락처·주소는 사용자 입력이 필요한데, 현재 `POST /brand-kits`가 요청 본문 없이 path 변수만 받고 있어 입력받을 자리가 없습니다. 이 부분은 프론트와 함께 봐야 할 것 같습니다.

## 4. BI 산출물 명칭 — 기획서와 맞춰주세요

요청서는 BI 브랜드킷을 **로션 병**으로 적으셨는데, 기획서 (5)·(7)의 정의는 **스마트스토어 규격 1000×1000 제품 썸네일**입니다. 로션 병은 그 썸네일 안에 들어가는 연출 소재라 상충하지는 않습니다.

정식 명칭은 `PRODUCT_THUMBNAIL`로 두되, **`BOTTLE`도 계속 받습니다.** 이미 배포하신 코드가 있어도 안 깨집니다. 교체는 편하실 때 하시면 됩니다.

## 5. 재생성 — `avoid_logos` 대신 `variant_offset`

지적하신 대로 `storage_key`는 AI 서버가 못 읽습니다. 그런데 **부정 프롬프트 자체가 필요 없습니다.**

`prompt_service`가 이미 `variant_index`로 모티프와 렌더링 방식을 순환 배정합니다. 최초 생성이 0~3을 쓰므로, 재생성 때 4~7을 쓰면 자동으로 다른 형태의 시안이 나옵니다.

```json
{ "...": "기존 필드 그대로", "num_variants": 4, "variant_offset": 4 }
```

`parent_generation_id`로 재시도 회차를 세신 뒤 `회차 × num_variants`를 넣어주시면 됩니다. 이미지 4장을 실어 보낼 필요가 없어 요청도 가볍습니다.

시드만 바꾸는 방식(4-4의 (c))은 효과가 약합니다. 같은 프롬프트에서 시드만 달라지면 색과 질감만 변하고 형태 아이디어는 그대로 나옵니다.

`avoid_logos`는 계속 보내셔도 무시됩니다. 회귀 테스트로 고정해 뒀습니다.

## 6. `ai_metadata_json`용 값 — 돌려드립니다

요청하신 대로 `/generate` 응답에 추가했습니다.

```json
{ "logos": [ { "imageBase64": "...", "seed": 2847193021, "variantIndex": 4 } ] }
```

기존 응답에 **추가만** 된 것이라 지금 붙어 있는 코드는 영향받지 않습니다. 두 값 다 `ai_metadata_json`에 저장하시면 됩니다.

## 7. 참고

- 브랜드킷은 임베딩·FAISS를 쓰지 않으므로 **`/health`가 `not_ready`여도 정상 동작**합니다. 상표 데이터를 아직 안 받으셨어도 브랜드킷 연동 테스트는 지금 가능합니다.
- `survey`는 스키마를 고정하지 않고 dict로 받습니다. 백엔드가 필드를 늘려도 AI 서버 재배포가 필요 없습니다.
- 백엔드에서 변경하신 테이블(`brand_kits`, `logo_downloads`, `pinned_at` 등)은 AI 서버와 무관해 그대로 진행하시면 됩니다.

## 8. 확인 부탁드리는 것

1. `card_info` — `Member.name`/`email`만 먼저 채워 보내는 것으로 시작하고, 직함·연락처는 `POST /brand-kits` 요청 본문 추가 + 프론트 입력 화면이 필요합니다
2. `BOTTLE` → `PRODUCT_THUMBNAIL` 교체 시점 (급하지 않음)
3. `avoid_logos` → `variant_offset` 교체 시점
