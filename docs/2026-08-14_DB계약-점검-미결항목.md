## 1. 설문 항목 3개가 DB에 컬럼이 없어 죽어 있음

**담당:** 기획 + 백엔드 + AI

AI 서버가 기능을 구현해 뒀는데 백엔드가 값을 보낼 방법이 없습니다.

| survey 키 | AI 서버 구현 | DB 컬럼 |
|---|---|---|
| `motif_category` | `MOTIF_CATEGORY_MAP` — 동물/생명체, 기하학적 도형, 원형/깔끔함, 보석/빛 | 없음 |
| `concreteness` | `CONCRETENESS_MAP` — 완전 추상 / 적당히 단순화 / 사실적 | 없음 |
| `text_color`, `include_brand_name_in_logo` | `logo_composer`에서 사용 | 없음 |

`ci_project`·`bi_project` 어디에도 컬럼이 없고 `ProjectLike.toSurvey()`도 넣지 않습니다.
결과적으로 `_resolve_motif`는 항상 업종 고정 목록으로 폴백하고 `concreteness_kw`는 항상 빈 문자열입니다.

`prompt_service.py` 주석에 이렇게 남아 있습니다.

> 예전엔 이 필드가 코드에서 아예 읽히지 않아서 "동물/생명체"·"기하학적 도형"을
> 골라도 항상 잎사귀·물방울 같은 보태니컬 모티프만 나오는 문제가 있었다(실측 확인됨).

AI 쪽은 고쳤지만 DB·백엔드가 따라오지 않아 **증상은 그대로**입니다.

**선택지**

- (a) V24로 컬럼 추가 + `toSurvey()` 수정 — 설문 화면에 이미 이 항목들이 있다면 이게 맞습니다
- (b) 화면에 없는 항목이면 AI 서버 코드를 정리 (죽은 채로 두지 않기)
- (c) 현행 유지 + "구현됐으나 미사용" 문서화

**먼저 확인할 것:** 화면설계서에 모티프 카테고리·구체성 항목이 있는지.

## 2. `logoStyle` 안전장치가 완전히 무력화됨

**담당:** AI + 백엔드 + 프론트

문자 전용 로고를 거절하는 규격이 실측 근거까지 갖춰 만들어져 있습니다.

```python
# schemas/similarity.py
logoStyle: Literal["combination", "symbol"] = "combination"
# 실측(scripts/calibrate_score.py, n=10/스타일) top-1 코사인 중앙값
#   워드마크 0.94, 레터마크 0.93  vs  혼합형 0.67, 심볼 0.59
# 등록 상표 간 최근접 중앙값(0.89)보다도 높아 오탐이 확실하다.
```

그런데 **두 군데서 동시에 죽어 있습니다.**

```java
// TrademarkAnalysisProcessor — 프로젝트의 실제 logo_style을 보지 않고 하드코딩
aiClient.search(Base64.getEncoder().encodeToString(png), "combination", 3);
```

```python
# routes/similarity.py — logoStyle을 서비스로 넘기지 않는다 (선언만 있고 사용처 0곳)
SimilarityService.process_similarity_search(req.imageBase64, top_k=req.topK)
```

**영향:** 워드마크·레터마크 로고가 그대로 분석됩니다. 코사인 0.94는 점수 환산
앵커(0.89 = 60점)를 넘으므로 **CAUTION 판정**이 납니다. 실제로는 안전한 로고에
"주의" 경고가 뜹니다.

**선택지**

- (a) 백엔드가 `logo_style`을 그대로 전달 → AI 서버 422 → 프론트에 "검사 불가" 안내 화면 필요
- (b) 백엔드에서 미리 걸러 분석을 시작하지 않고 별도 상태로 저장 (DB 상태값 추가 필요)
- (c) 분석은 하되 문자 전용 스타일 점수 보정 — 근거 데이터 추가 수집 필요

**같이 볼 것:** `logo_style`은 CHECK 없는 `varchar(50)`입니다. 값 집합을 확정하려면
`chk_logo_style` 추가를 함께 검토하는 편이 좋습니다 (아래 6번과 연결).

## 3. CI 핵심가치가 프롬프트에서 통째로 생략됨

**담당:** 기획 + 백엔드

CI는 기업 가치를 자유 서술 한 칸(`core_values varchar(300)`)으로만 받습니다.
BI와 달리 칩 컬럼(`value_category_1~3`)이 없습니다.

```java
// CiProject.toSurvey
survey.put("company_values_text", coreValues);   // company_values(칩)는 없음
```

`_resolve_values`는 칩이 없으면 자유 서술을 쉼표로 쪼개 `VALUE_KEYWORD_MAP`에서
찾고, **못 찾은 한글 토큰은 버립니다.**

```python
elif not _HANGUL.search(t):
    usable.append(t)   # 영문일 때만 통과
if not usable:
    return ""          # 전부 한글이면 문장 자체를 생략
```

사전의 15개 단어(`비건`, `프리미엄`, `클린뷰티` …)와 정확히 일치하지 않는 한
CI 사용자가 적은 핵심가치는 프롬프트에 **한 글자도 들어가지 않습니다.**
"신뢰와 혁신을 추구하는 기업" 같은 자연스러운 입력은 전부 버려집니다.

한글을 그대로 넣지 않는 것 자체는 맞습니다 — 주석에 "영문 프롬프트 한복판에
한글 조각이 박힌다(실측 확인됨)"는 근거가 있습니다. 문제는 **대안이 없다는 것**입니다.

**선택지**

- (a) `ci_project`에도 `value_category_1~3` 추가 (BI와 동일 구조) — 스키마 변경
- (b) 자유 서술을 LLM으로 영문 키워드화 (`note_service`가 이미 Gemini를 쓰므로 경로는 있음)
- (c) 현행 유지 — CI는 업종·톤·색상·스타일만으로 생성

## 4. `matches.size() != topK` 를 오류로 처리

**담당:** 백엔드

```java
// FastApiLogoAiClient.search
if (disclaimer == null || disclaimer.isBlank() || matches.size() != topK) {
    throw new ApiException(ErrorCode.AI_INVALID_RESPONSE);
}
```

AI 서버는 메타데이터가 깨진 행을 의도적으로 건너뜁니다.

```python
if not app_no or not image_path:
    logger.warning("Skipping match with incomplete metadata: index=%s", ...)
    continue
```

`topK=3`을 요청했는데 결손으로 2건만 오면 백엔드가 **분석 전체를 실패 처리**합니다.
부분 결과를 보여줄 수 있는 상황인데 아무것도 못 보여줍니다.

**제안:** `matches.isEmpty()`만 오류로 보고, 부족한 개수는 경고 로그로 남기기.
다른 항목과 달리 판단이 단순해 바로 처리 가능합니다.

## 5. `schema.sql`에 CHECK 제약 19개 누락

**담당:** 백엔드

`database/schema.sql`(로컬 개발 DB 생성용)에 CHECK가 **22개 중 3개만** 있습니다.
UNIQUE 6개와 INDEX 6개는 정상입니다.

**있는 것:** `chk_download_project_type`, `chk_generation_project_exclusive`, `chk_kit_type`

**빠진 것 (19):**

```
chk_ci_project_status    chk_bi_project_status     chk_generation_status
chk_ci_current_step      chk_bi_current_step       chk_candidate_order
chk_ci_color_1 ~ 4       chk_bi_color_1 ~ 4        chk_analysis_status
                         chk_bi_target_age         chk_analysis_similarity
                                                   chk_analysis_risk
                                                   chk_match_similarity
```

**영향:** 로컬에서는 통과하는데 운영에서 터집니다. 아래 값들이 로컬 DB에는 그냥 들어갑니다.

- `trademark_analyses.risk_level = 'LOW'` (허용값: SAFE/MODERATE/CAUTION)
- `trademark_matches.similarity = 250` (허용 범위 0~100)
- `logo_candidates.candidate_order = 7` (허용 범위 1~4)
- `ci_project.color_1 = 'blue'` (HEX 형식이어야 함)

로컬 테스트를 통과한 코드가 팀 공용 DB에서 실패합니다.

**조치:** 각 `CREATE TABLE`에 V23 기준 CHECK 19개 추가. 원본은 `V11`(status/step/color/order),
`V22`(kit_type), `V23`(step 범위 수정본)에 있습니다. 헤더 주석의 "Flyway V1-V19"도
현재 V23으로 갱신 필요.

## 6. 조건부 마이그레이션 V20·V23의 사각지대

**담당:** 백엔드

V20·V23은 조건이 안 맞으면 **아무것도 안 하고 성공 처리**됩니다. 재실행 안전성을 위한
설계지만 빠져나가는 경우가 있습니다.

**V23** — 판단 기준이 `color_1`의 NOT NULL 여부 하나인데, 같은 마이그레이션이
`current_step` 범위 수정도 함께 합니다.

| | V11 (초기) | V23 (수정 후) | 명세서 v2.1 |
|---|---|---|---|
| `chk_ci_current_step` | 1~4 | **1~5** | 1~5 |
| `chk_bi_current_step` | 1~5 | **1~6** | 1~6 |

`schema.sql`로 만든 DB는 color_1이 처음부터 nullable이라 V23이 스킵됩니다.
그런 DB에 V11 이력이 섞여 있으면 범위가 1~4로 남아 **CI 5단계 진입 시 DB가 거부**합니다.

**V20** — `logo_generations`·`logo_candidates`가 **둘 다 0행일 때만** 실행됩니다.
데이터가 하나라도 있으면 `parent_generation_id`가 생기지 않고, 엔티티는 이 컬럼을
요구하므로 `ddl-auto=validate` 환경에서 **애플리케이션 기동이 실패**합니다.
재생성(F12-2) 기능도 동작하지 않습니다.

**확인용 SQL** (읽기 전용, 공용 DB에 그대로 실행 가능)

```sql
-- 1) current_step 범위 (1 AND 5 / 1 AND 6 이어야 정상)
SELECT CONSTRAINT_NAME, CHECK_CLAUSE
  FROM information_schema.CHECK_CONSTRAINTS
 WHERE CONSTRAINT_SCHEMA = DATABASE()
   AND CONSTRAINT_NAME IN ('chk_ci_current_step','chk_bi_current_step');

-- 2) parent_generation_id 존재 (1행 나와야 정상)
SELECT COLUMN_NAME FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'logo_generations'
   AND COLUMN_NAME = 'parent_generation_id';

-- 3) CHECK 제약 전수 (22개 나와야 정상)
SELECT COUNT(*) FROM information_schema.CHECK_CONSTRAINTS
 WHERE CONSTRAINT_SCHEMA = DATABASE() AND CONSTRAINT_NAME LIKE 'chk\_%';
```

# 부록: 개인 환경 확인 사항

저장소 문제는 아니지만, 각자 로컬에 아래 파일이 있으면 확인해 주세요.

git에 추적되는 설정은 전부 안전합니다 (`application-local.properties`,
`application-prod.properties` 모두 `ddl-auto=validate`, `flyway.enabled=false`).

그런데 **추적되지 않는 로컬 파일**이 이걸 뒤집을 수 있습니다.

```yaml
# backend/src/main/resources/application.yml  (untracked)
spring:
  profiles:
    active: dev          # local 이 아니라 dev

# backend/src/main/resources/application-dev.yml  (untracked)
spring:
  jpa:
    hibernate:
      ddl-auto: update   # Hibernate가 스키마를 자동 변경
```

`ddl-auto: update`는 엔티티와 다른 테이블을 만나면 컬럼을 자동으로 추가·변경합니다.
Flyway로 관리하는 스키마에 끼어들면 마이그레이션 이력과 실제 DB가 어긋납니다.
`SPRING_DATASOURCE_URL`을 공용 DB로 준 채 dev 프로파일로 뜨면 공용 스키마가 변형될 수 있습니다.

이 두 파일은 `brandloop_user` / `brandloop` DB를 가리키는데, 같이 untracked로 남아 있는
`backend/src/main/java/com/brandloop/`, `backend/build.gradle`, `backend/settings.gradle`과
함께 프로젝트명이 brandloop이던 시절의 잔재로 보입니다. 삭제하거나
`ddl-auto: validate`로 바꿔 두시길 권합니다.
