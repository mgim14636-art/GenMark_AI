# FastAPI AI Server API Documentation

## Endpoints

- `GET /health` - Health check status
- `POST /api/v1/generation/generate` - Generate logo from text prompt via FLUX model
- `POST /api/v1/embedding/extract` - Extract feature vector via DINOv2
- `POST /api/v1/similarity/search` - Search top-K similar trademark vectors in FAISS

## 상표 유사도 분석 (POST /api/v1/similarity/search)

담당: 남현욱 · 기준 문서: GenMark AI Backend API Specification v1.0 (11장)

### 요청

```json
{
  "imageBase64": "...",
  "logoStyle": "combination",
  "topK": 3
}
```

### 응답

```json
{
  "maxSimilarity": 27,
  "riskLevel": "SAFE",
  "matches": [
    {
      "rank": 1,
      "applicationNumber": "4020200003334",
      "name": "OLIVE YOUNG AWARDS",
      "category": "화장품 · 도형복합",
      "similarity": 27,
      "imagePath": "raw/cosmetic/.../4020200003334_tm000001.jpg"
    }
  ],
  "disclaimer": "본 분석은 로고 이미지의 시각적 유사성을 보여주는 참고 자료이며, 상표 등록 가능 여부나 법적 침해 여부를 판단하지 않습니다."
}
```

`riskLabel`, `riskDescription`은 백엔드에서 매핑하는 것을 제안합니다. 문구 변경 시 AI 서버 재배포가 불필요하기 때문입니다.

## 유사도 점수 산정

명세 11.4의 3구간(0~29 안전 / 30~59 보통 / 60~100 주의)은 그대로 유지합니다.

단, 응답의 `similarity`는 모델의 원시 코사인 유사도가 아니라 **실측 분포 기반 백분위 점수**입니다.

보유 상표 670건의 전체 쌍(224,115건) 측정 결과:

| 지표 | 코사인 유사도 |
|---|---|
| 평균 | 0.493 |
| 상위 50% | 0.508 |
| 상위 10% | 0.678 |
| 상위 5% | 0.722 |
| 상위 1% | 0.803 |

DINOv2의 코사인 유사도는 서로 무관한 상표 간에도 평균 0.49가 나옵니다. 이 값을 그대로 백분율로 환산하면 무관한 상표의 약 25%가 "주의" 등급으로 분류됩니다. 따라서 원시 유사도를 위 분포상의 백분위로 변환해 0~100 정수로 반환합니다.

1. 비엔나 분류코드 교집합 기반 템플릿 문구 — 구현 가능, 근거 명확 **(권장)**

## 유사도 점수 산정

### 처리 흐름

1. DINOv2로 이미지를 768차원 벡터로 변환, L2 정규화
2. 보유 상표 670건 전체와 코사인 유사도 계산
3. **해당 쿼리의 점수 분포 기준으로 z-score 정규화**
4. `similarity = z × 20` (0~100 범위)
5. 명세 11.4 구간으로 등급 판정 (0~29 SAFE / 30~59 MODERATE / 60~100 CAUTION)

### 실험 1 — 왜 원시 유사도를 그대로 쓰지 않는가

상표 670건의 전체 쌍(224,115건) 유사도 분포:

| 지표 | 코사인 유사도 |
|---|---|
| 평균 | 0.493 |
| 상위 10% | 0.678 |
| 상위 5% | 0.722 |
| 상위 1% | 0.803 |

DINOv2의 코사인 유사도는 서로 무관한 상표 간에도 평균 0.49가 나옵니다. 생성 로고는 상표 이미지와 공통 특성(흰 배경, 단순 벡터 형태)을 공유해 절대값이 더 높게 나오므로, 상표 간 분포를 기준으로 백분위를 매기면 **육안상 유사하지 않은 로고도 98점(CAUTION)** 으로 분류되는 문제가 확인되었습니다.

따라서 쿼리별 점수 분포를 기준으로 z-score를 산출합니다. "이 상표가 나머지 상표들 대비 얼마나 더 유사한가"를 측정하며, 공통 배경 요인이 평균에 흡수되어 상쇄됩니다. 동일 케이스에서 48점(MODERATE)으로 조정되어 육안 판단과 일치했습니다.

### 실험 2 — 콤비네이션 형식 한정 근거

동일한 생성 로고에 대해 심볼 단독과 텍스트 결합 형태를 비교한 결과:

| 쿼리 | 심볼만 | 텍스트 결합 |
|---|---|---|
| 기하학 도형 로고 | z 4.54 (오탐) | z 2.39 |
| 식물 모티프 로고 | z 3.59 | z 3.89 |

데이터셋이 도형+문자 결합 상표(도형복합)로 구성되어 있어, 심볼 단독 쿼리는 레이아웃 불일치로 인한 오탐이 발생했습니다. 기하학 도형 로고가 형태적으로 무관한 상표와 z 4.54로 매칭된 사례가 이에 해당하며, 텍스트 결합 후 z 2.39로 정정되었습니다.

**따라서 유사도 분석 대상은 텍스트가 결합된 최종 로고로 한정합니다.** 생성 파이프라인은 심볼 단독이 아닌 완성 로고를 전달해야 합니다.

### 실험 3 — 데이터 규모 영향

동일 쿼리에 대해 데이터셋 크기를 달리해 측정:

| 데이터 규모 | 최대 z |
|---|---|
| 335건 | 2.52 |
| 670건 | 2.62 |

표본을 2배로 늘렸을 때 z 변화는 0.10 수준으로, 정규화 방식이 데이터 규모에 강건함을 확인했습니다. 데이터 확장 시 판정 로직 변경 없이 스케일 계수(현재 20) 재확인만 필요합니다.

단, 데이터가 증가하면 실제 유사 상표를 포착할 확률이 높아지므로, 검색 품질 자체는 규모에 비례해 향상됩니다.

단, 데이터 증가에 따라 실제 유사 상표를 포착할 확률은 높아지므로 검색 품질 자체는 규모에 비례해 향상됩니다.

### 실험 4 — 색채 영향

동일 이미지의 색상 반전 시 유사도 0.731, 그레이스케일 변환 후에도 0.715로 유사한 수준이었습니다. 모델이 색조보다 명암 구조를 반영함을 시사하며, 실제 상표 데이터는 흰 배경이 표준이므로 실무상 영향은 제한적입니다.

판례상 도형상표는 외관, 그중에서도 형상·구도가 지배적 인상을 결정하며 색채는 부수적 요소입니다. 실제 검색에서 색상이 다른 상표가 형태 유사성으로 상위에 검색되는 것을 확인했습니다.

### 08/05 오후 변경사항 

## 유사도 점수 산정

### 처리 흐름

1. DINOv2(`facebook/dinov2-base`)로 이미지를 768차원 벡터로 변환, L2 정규화
2. FAISS IndexFlatIP로 보유 상표 7,423건과 코사인 유사도 계산
3. 해당 쿼리의 점수 분포 기준으로 z-score 정규화
4. `similarity = 13.7 × z − 7.3` (0~100 범위)
5. 명세 11.4 구간으로 등급 판정 (0~29 SAFE / 30~59 MODERATE / 60~100 CAUTION)

투명 배경(RGBA) 이미지는 흰 배경으로 합성 후 처리합니다. KIPRIS 상표 이미지가 모두 흰 배경이므로 조건을 맞추지 않으면 투명 영역이 검은색으로 변환되어 임베딩이 어긋납니다.

### 실험 1 — 원시 유사도를 쓰지 않는 이유

상표 간 유사도 분포 (2,000건 샘플, 399만 쌍):

| 지표 | 코사인 유사도 |
|---|---|
| 평균 | 0.488 |
| 상위 10% | 0.675 |
| 상위 5% | 0.718 |
| 상위 1% | 0.798 |

DINOv2의 코사인 유사도는 서로 무관한 상표 간에도 평균 0.49가 나옵니다. 생성 로고는 상표 이미지와 공통 특성(흰 배경, 단순 벡터 형태)을 공유해 절대값이 더 높게 나오므로, 상표 간 분포 기준으로 백분위를 매기면 육안상 유사하지 않은 로고도 98점(CAUTION)으로 분류되는 문제가 확인되었습니다.

따라서 쿼리별 점수 분포를 기준으로 z-score를 산출합니다. "이 상표가 나머지 상표들 대비 얼마나 더 유사한가"를 측정하며, 공통 배경 요인이 평균에 흡수되어 상쇄됩니다.

### 실험 2 — 콤비네이션 형식 한정 근거

동일 생성 로고에 대해 심볼 단독과 텍스트 결합 형태를 비교:

| 쿼리 | 심볼만 | 텍스트 결합 |
|---|---|---|
| 기하학 도형 로고 | z 4.54 (오탐) | z 2.39 |
| 식물 모티프 로고 | z 3.59 | z 3.89 |

데이터셋이 도형+문자 결합 상표(도형복합)로 구성되어 있어, 심볼 단독 쿼리는 레이아웃 불일치로 인한 오탐이 발생했습니다. 기하학 도형 로고가 형태적으로 무관한 상표와 z 4.54로 매칭된 사례가 이에 해당하며, 텍스트 결합 후 z 2.39로 정정되었습니다.

**유사도 분석 대상은 텍스트가 결합된 최종 로고로 한정합니다.** 생성 파이프라인은 심볼 단독이 아닌 완성 로고를 전달해야 합니다.

참고로 순수 도형상표는 3류 등록 기준 62건에 불과해 별도 인덱스 구성이 어렵습니다. 데이터 확장 시 `logoStyle`에 따라 인덱스를 분리하는 것을 고도화 과제로 둡니다.

### 실험 3 — 데이터 규모의 영향

| 데이터 규모 | 동일 쿼리의 최대 z |
|---|---|
| 335건 | 2.52 |
| 670건 | 2.62 |
| 7,423건 | 3.66 |

335 → 670건 구간에서는 z 변화가 0.10 수준이었으나, 7,423건으로 확장하자 z가 크게 상승했습니다. 원인은 최대 코사인 값이 아니라 **분포의 평균**입니다.

| 데이터 규모 | 최대 cos | 평균 cos | 표준편차 |
|---|---|---|---|
| 670건 | 0.776 | 0.523 | 0.104 |
| 7,423건 | 0.746 | 0.404 | 0.094 |

데이터가 늘면서 쿼리와 무관한 형태의 상표가 대량 포함되어 평균이 낮아졌고, 최대값은 오히려 떨어졌음에도 z는 상승했습니다.

**따라서 z 값의 절대 크기는 데이터 규모에 의존하며, 데이터 확장 시 스케일 재조정이 필요합니다.** 이 문제를 해결하기 위해 실험 4의 앵커링 방식을 도입했습니다.

### 실험 4 — 판정 기준의 앵커링

스케일 계수를 임의로 정하지 않고, **보유 데이터 자체에서 기준선을 도출**했습니다.

보유 상표 200건을 무작위 추출해 각각을 쿼리로 넣고, 자기 자신과 중복 상표를 제외한 1위 매치의 z를 측정했습니다.

| 지표 | 1위 매치의 z |
|---|---|
| 평균 | 3.11 |
| 중앙값 | 2.72 |
| 상위 10% | 4.31 |
| 상위 5% | 4.91 |
| 상위 1% | 9.48 |

**이 상표들은 모두 특허청 심사를 통과해 공존 등록된 것들입니다.** 즉 서로 비유사로 판단받아 함께 등록이 허용된 쌍이므로, 이 수준의 유사도는 실무상 문제되지 않는 범위로 볼 수 있습니다.

이를 근거로 두 지점을 앵커로 삼아 선형 매핑했습니다.

| 앵커 | z | 점수 |
|---|---|---|
| 등록 상표 간 1위 중앙값 | 2.72 | 30 (SAFE / MODERATE 경계) |
| 등록 상표 간 1위 상위 5% | 4.91 | 60 (MODERATE / CAUTION 경계) |

두 항목 모두 **구현 완료 상태이며, 아래 규격이 확정본**입니다. 백엔드는 이 문서대로 붙이면 됩니다.

## 1. 브랜드킷 (POST /api/v1/generation/brand-kit)

### 1-1. 산출 방식 — 로고를 이미지 생성 모델에 넣지 않습니다

요청서 3-3에서 협의 항목으로 남겨두신 부분에 대한 답입니다.

현재 FLUX 호출부(`flux_service._call_flux_klein`)는 `prompt / width / height / seed / steps / samples`만 보내는 **text-to-image 전용** 경로이고, 설령 image-to-image가 열려도 디퓨전 모델은 입력 로고를 그대로 재현하지 못합니다. 브랜드 아이덴티티 산출물에서 사용자의 로고가 변형돼 나오면 기능 자체가 무의미해집니다.

따라서 **배경만 생성하고 로고는 PIL로 정확히 합성**합니다. 이는 기획서 (7) 수행방법의 다음 항목과 동일한 방침입니다.

> CI 명함: 레이아웃 템플릿 + 로고·폰트·사용자 정보 합성 (정보 정확도 확보를 위해 이미지 생성 모델 미사용)
> BI 썸네일: FLUX.2 [klein] 4B로 제품 연출 배경 생성 후 로고·제품명 폰트 레이어 합성, 1000×1000 규격 산출

### 1-2. kit_type

| 값 | 산출물 | 규격 | 외부 API |
|---|---|---|---|
| `BUSINESS_CARD` | 명함 | 1063 × 591 (90×50mm @300dpi) | 없음 |
| `PRODUCT_THUMBNAIL` | 제품 썸네일 | 1000 × 1000 | FLUX (연출 배경) |
| `BOTTLE` | `PRODUCT_THUMBNAIL`의 별칭 | 동일 | 동일 |

요청서에는 BI 산출물이 "로션 병"으로 되어 있는데, 기획서 (5)·(7)의 정의는 **스마트스토어 규격 1000×1000 제품 썸네일**입니다. 로션 병은 그 썸네일 안에 들어가는 연출 소재이므로 상충하지 않으며, 정식 명칭만 `PRODUCT_THUMBNAIL`로 둡니다. 이미 배포된 백엔드 코드가 있을 수 있어 `BOTTLE`도 계속 받습니다.

### 1-3. 요청

요청 본문은 제안하신 snake_case를 그대로 씁니다(기존 `/generate`도 snake_case 설문 필드를 받습니다). 응답만 `/generate`의 `logos[].imageBase64`와 맞춰 camelCase입니다.

```json
{
  "kit_type": "BUSINESS_CARD",
  "logo_image_base64": "iVBORw0KGgo...",
  "ci_bi": "CI",
  "survey": {
    "company_name": "젠마크",
    "industry": "COSMETICS",
    "tone": "friendly",
    "colors": ["#4F46E5", "#EC4899"],
    "logo_style": "combination"
  },
  "card_info": {
    "name": "남현욱",
    "title": "대표",
    "company": "주식회사 젠마크",
    "phone": "010-1234-5678",
    "email": "wook@genmark.ai",
    "address": "광주광역시 남구 송암로 60"
  },
  "product_name": "수분 세럼"
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `kit_type` | O | 위 표의 3개 값 중 하나. 그 외는 422 |
| `logo_image_base64` | O | 완성 로고 PNG의 Base64. `data:image/png;base64,` 접두어도 허용 |
| `ci_bi` | X | 로그·분기 참고용 |
| `survey` | X | 로고 생성 때 넘긴 것과 같은 구조. **스키마를 고정하지 않고 dict로 받습니다** — 백엔드가 필드를 늘려도 AI 서버 재배포가 필요 없습니다. 현재 실제로 읽는 값은 `colors`(또는 `color_manual`) 첫 번째 HEX와 `company_name`/`brand_name`뿐입니다 |
| `card_info` | X | 명함에 인쇄할 사용자 정보. 없으면 회사명만 넣은 브랜드 카드로 합성되고 `preliminary: true`가 됩니다 |
| `product_name` | X | 썸네일 하단 문구. 없으면 `survey`의 브랜드명 사용 |

**`card_info`는 요청서 3-2 예시에 없던 신규 항목입니다.** 기획서의 "사용자 정보(이름·직함·연락처)를 합성"에 해당합니다.

현재 `BrandKitProcessor.buildRequest`는 `kit_type / logo_image_base64 / survey / ci_bi` 네 가지만 보내고 있어, 이를 필수로 잡으면 CI 브랜드킷이 전부 `FAILED`로 끝납니다. 그래서 **선택 항목으로 두고, 없으면 회사명만 넣은 브랜드 카드로 합성한 뒤 `preliminary: true`와 `warnings`로 알립니다.** 레이아웃은 동일하므로 나중에 값이 채워지면 그대로 명함이 됩니다.

`Member` 엔티티에 `name`과 `email`이 이미 있으므로, 화면 없이도 그 둘만 먼저 채워 보내실 수 있습니다. 직함·연락처·주소는 사용자 입력이 필요합니다. 현재 `POST /brand-kits`는 요청 본문이 없어 입력받을 자리가 없다는 점도 함께 봐주세요.

`logo_image_base64` 전달 방식은 **Base64 유지**를 제안합니다. AI 서버는 백엔드 스토리지(`storage_key`)에 접근 권한이 없고, `/similarity/search`도 이미 Base64로 받고 있어 일관됩니다.

### 1-4. 응답

```json
{
  "kitType": "BUSINESS_CARD",
  "imageBase64": "iVBORw0KGgo...",
  "images": [
    { "imageBase64": "iVBORw0KGgo...", "width": 1063, "height": 591 }
  ],
  "preliminary": false,
  "warnings": [],
  "elapsedMs": 1447
}
```

| 필드 | 설명 |
|---|---|
| `kitType` | 정규화된 값. `BOTTLE`로 보내도 `PRODUCT_THUMBNAIL`이 돌아옵니다 |
| `imageBase64` | **최상위 호환 필드.** `FastApiBrandKitAiClient`가 `body.get("imageBase64")`를 읽고 있어, 백엔드 수정 없이 붙도록 `images[0]`을 그대로 복제해 둡니다 |
| `images` | 정식 필드. 현재는 1장이지만 명함 앞/뒤, 썸네일 각도 변형으로 늘어날 여지를 둡니다 |
| `preliminary` | `true`면 최종 품질이 아닌 임시 합성 결과 |
| `warnings` | `preliminary`인 이유. 로깅용이며 비어 있을 수 있습니다 |
| `elapsedMs` | AI 서버 내부 소요 시간 |

**백엔드는 지금 코드 그대로 두셔도 동작합니다.** `images[]`로 옮기는 건 여유 있을 때 하시면 됩니다.

### 1-5. 현재 구현 상태

| kit_type | 상태 | preliminary |
|---|---|---|
| `BUSINESS_CARD` (`card_info` 있음) | **완료.** 좌(로고) / 우(인적사항) 2단 템플릿 합성 | `false` |
| `BUSINESS_CARD` (`card_info` 없음) | 회사명만 넣은 브랜드 카드로 합성 | `true` |
| `PRODUCT_THUMBNAIL` | **완료.** FLUX(`black-forest-labs/flux.2-pro`)가 브랜드명이 적힌 제품 용기 사진을 직접 생성하고, 그 위에 제품명·헤드라인은 PIL로 정확히 얹음. AI 호출이 실패하면(키 미설정·네트워크 오류 등) 톤 기반 그라데이션 + 중앙 로고로 자동 대체 | 성공 시 `false`, 대체 시 `true` |

`preliminary=true`가 뜨는 경우는 "AI 제품 사진 생성 실패로 그라데이션 대체" 또는 "`card_info` 없음" 뿐입니다. 응답 형식·규격은 두 경우 모두 확정본과 동일합니다.

**참고**: 제품 용기·라벨의 브랜드명은 AI가 직접 그리므로, 실제 업로드된 로고 이미지와 픽셀 단위로 동일하지는 않습니다(한글 브랜드명은 특히 철자가 흔들릴 수 있음). 제품명·헤드라인 텍스트는 정확도가 중요해 PIL로 별도 합성합니다.

기존 계약과 같이 `{"code": ..., "message": ...}` 형식입니다.

| HTTP | code | 상황 | 재시도 |
|---|---|---|---|
| 400 | `BRANDKIT_INVALID_IMAGE` | `logo_image_base64` 디코드 실패 / 이미지 아님 / 8px 미만 | 무의미 |
| 422 | `SIMILARITY_INVALID_REQUEST` | 스키마 불일치(알 수 없는 `kit_type` 등) | 무의미 |
| 500 | `BRANDKIT_COMPOSITION_FAILED` | 합성 중 예기치 못한 오류 | 가능 |

입력값은 에러 응답·로그에 되비치지 않습니다(Base64 유출 방지, 계약 §11 동일 적용).

브랜드킷은 임베딩·FAISS를 쓰지 않으므로 **`/health`가 `not_ready`여도 정상 동작**합니다. 상표 데이터 미준비 상태에서도 연동 테스트가 가능합니다.

## 2. 재생성 (POST /api/v1/generation/generate)

### 2-1. `avoid_logos` 대신 `variant_offset`을 제안합니다

요청서 4-4에서 지적하신 대로 `storage_key`는 AI 서버가 읽을 수 없어 그대로는 효과가 없습니다. 그런데 **부정 프롬프트 자체가 필요 없습니다.**

`prompt_service.build_prompt_from_survey(survey, variant_index=i)`가 이미 `variant_index`로 모티프와 렌더링 방식을 순환 배정합니다. 최초 생성은 0~3을 쓰므로, 재생성 때 4~7을 쓰면 **자동으로 다른 형태의 시안이 나옵니다.**

| 방식 | 요청 크기 | 정확도 | 판단 |
|---|---|---|---|
| (a) 이전 로고 4장 Base64 | 수 MB | 높음 | 요청이 무거움 |
| (b) 텍스트 설명 | 작음 | 낮음 | 부정확 |
| (c) 시드 회피 | 작음 | 낮음 | 시드만 바꿔도 모티프는 그대로 |
| **(d) variant_offset** | **정수 1개** | **높음** | **채택** |

(c)가 효과가 약한 이유는, 같은 프롬프트에서 시드만 바꾸면 색·질감만 달라지고 형태 아이디어는 유지되기 때문입니다. 모티프 자체를 바꿔야 "다른 시안"이 됩니다.

### 2-2. 요청 추가 필드

```json
{
  "ci_bi": "CI",
  "company_name": "젠마크",
  "...": "기존 필드 그대로",

  "num_variants": 4,
  "variant_offset": 4
}
```

| 필드 | 기본값 | 설명 |
|---|---|---|
| `variant_offset` | `0` | 재생성 N회차 = `N × num_variants`. 최초 생성은 생략하거나 0. 범위 0~64 |

백엔드가 이미 추가하신 `logo_generations.parent_generation_id`로 재시도 회차를 셀 수 있으므로, 그 값에 `num_variants`를 곱해 넣어주시면 됩니다.

`avoid_logos`를 계속 보내셔도 됩니다 — `GenerationRequest`에 `extra="forbid"`가 없어 무시되며, 회귀 테스트(`test_generation_ignores_unknown_keys`)로 고정해 두었습니다.

### 2-3. 응답 추가 필드 — `ai_metadata_json` 활용

요청서 4-4의 3번 항목입니다. 시드와 모티프 인덱스를 돌려드립니다.

```json
{
  "logos": [
    { "imageBase64": "iVBORw0KGgo...", "seed": 2847193021, "variantIndex": 4 },
    { "imageBase64": "iVBORw0KGgo...", "seed":  938471002, "variantIndex": 5 }
  ]
}
```

| 필드 | 설명 |
|---|---|
| `variantIndex` | 이 시안에 배정된 모티프 인덱스 (`variant_offset + i`) |
| `seed` | 생성에 쓴 시드. OpenRouter Image API의 `seed` 파라미터로 넘긴 값이며, flux.2-pro 엔드포인트가 이를 지원함을 `images/models/black-forest-labs/flux.2-pro/endpoints`에서 확인했습니다 |

기존 응답에 **추가만** 된 것이라 지금 붙어 있는 소비자는 영향받지 않습니다. `logo_candidates.ai_metadata_json`에 그대로 저장하시면, 나중에 "몇 회차까지 재생성했는지"와 "어떤 모티프가 선택률이 높은지"를 추적할 수 있습니다.

## 3. 백엔드에서 확인 부탁드리는 것

1. `card_info` 입력 화면이 필요합니다 (이름·직함·회사명·연락처·이메일·주소). 없어도 실패하지는 않지만 명함에 인적사항이 비어 나갑니다. `POST /brand-kits`에 요청 본문을 추가하는 작업이 함께 필요합니다.
2. BI 산출물 명칭을 `PRODUCT_THUMBNAIL`로 맞출지, `BOTTLE`을 계속 쓸지. 둘 다 동작하므로 급하지 않습니다.
3. `avoid_logos` → `variant_offset` 교체 시점.
